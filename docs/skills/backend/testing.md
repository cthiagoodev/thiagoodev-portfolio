# Backend Testing

Test-Driven Development (TDD) is the core development strategy for all backend code under `services/app-api`. Tests define the contract, structure, and design before implementation begins.

## TDD Workflow: Red-Green-Refactor

All features, entities, use cases, and repository adapters must be implemented following the TDD cycle:

```text
1. RED      → Escreva o teste primeiro, definindo o comportamento esperado. Execute `go test ./...` e veja-o falhar.
2. GREEN    → Escreva a implementação mínima necessária para fazer o teste passar.
3. REFACTOR → Melhore a legibilidade, arquitetura e performance sem alterar o comportamento, mantendo a suíte verde.
```

## AAA Pattern (Arrange, Act, Assert)

Every test scenario must follow the **AAA** structure separated strictly by distinct blank-line blocks.

- **No Comment Rule**: Test code must contain **NO COMMENTS**. Do NOT add `// Arrange`, `// Act`, or `// Assert` comments.
- **Blank-line Blocks**:
  1. **Arrange**: Input variables, test fixtures, and mock setup/expectations.
  2. **Act**: Execution of the constructor, method, or use case under test.
  3. **Assert**: Verifications (`require.NoError`, `assert.Equal`, `assert.True`, etc.).

## Test Naming Convention

Tests must use descriptive, behavior-driven names following the pattern:

```text
Test<Target>_<ExpectedBehavior>[_<Condition>]
```

### Examples:
- `TestNewProject_Success`
- `TestNewProject_ValidationError_EmptyName`
- `TestNewAbout_Success`
- `TestNewAbout_ValidationError_EmptyName`
- `TestGetAboutUseCase_Success`
- `TestGetAboutUseCase_NotFound`
- `TestAboutHandler_Get_Success`
- `TestAboutDatabaseRepository_Get_Success`

## Test Boundaries

Choose the smallest test boundary that provides meaningful confidence:

- **Domain Entities & Value Objects**: Pure unit tests without mocks (`_test.go` in separate package, e.g. `package entities_test`). Verify invariants, default values, and sentinel error wrapping (`errors.Is`).
- **Application Use Cases**: Test with mocks for external boundaries (repositories, external clients) generated by Mockery (`testify/mock`).
- **HTTP Transport / Presentation (`internal/presentation/handlers`)**: Test handlers isoladamente com `httptest.NewRecorder` e mocks do caso de uso; assert status codes, headers, and response payloads.
- **Database Repositories (`internal/infrastructure/repositories`)**: Integration tests against real PostgreSQL instances (via Docker) to validate SQL queries, constraints, and data mapping.
- **Feature Modules (`internal/modules/<feature>`)**: Teste unitário de instanciamento do módulo da feature. **Não** crie testes unitários para o agregador raiz (`internal/modules/module.go`) nem para o roteador (`internal/router/router.go`), pois eles não carregam regra de negócio e a lógica já é coberta nos testes do handler e do módulo da feature.
- **Do not mock pure transformations**: Keep tests simple, fast, and deterministic.

## Padrões para Testes de Integração

Para testes que tocam infraestrutura real (banco de dados PostgreSQL, sockets de rede, filesystem), seguimos os 3 padrões canônicos da comunidade Go:

### 1. Separação por Build Tags (`//go:build integration`)
- Arquivos de teste de integração devem possuir o sufixo `*_integration_test.go` e declarar a diretiva de compilação no topo do arquivo:
  ```go
  //go:build integration

  package database_test
  ```
- **Testes Unitários Rápidos (Padrão)**:
  ```bash
  go test ./...
  ```
  *(O compilador Go ignora automaticamente os arquivos etiquetados com `integration`, mantendo o ciclo de TDD diário ultrarrápido).*
- **Execução da Suíte de Integração**:
  ```bash
  go test -tags=integration -v ./...
  ```

### 2. Pacotes de Testes Externos (`package <pacote>_test`)
- Todos os arquivos de teste (unitários e de integração) devem utilizar pacotes externos com o sufixo `_test` (ex.: `package database_test`, `package handlers_test`, `package usecases_test`).
- **Motivo**: Previne ciclos de dependência (*import cycles*) e garante que o teste consuma a API pública do componente exatamente como os consumidores reais.

### 3. A Flag de Tempo `testing.Short()`
- Nos testes de integração, verifique sempre se o desenvolvedor solicitou execução rápida:
  ```go
  if testing.Short() {
      t.Skip("skipping integration test in short mode")
  }
  ```
- Permite rodar `go test -short ./...` pulando testes pesados ou que exigem containers ativos.

### 4. Limpeza Automática com `t.Cleanup`
- Utilize `t.Cleanup(func() { ... })` para desalocar recursos, fechar pools de conexão ou truncar tabelas ao final do teste:
  ```go
  t.Cleanup(func() {
      pool.Close()
  })
  ```
- Garante limpeza mesmo se o teste falhar no meio com `require.FailNow` ou `t.Fatal()`.

### 5. Table-Driven Tests
- Agrupe variações de cenários em structs anônimas dentro do teste para reutilizar fixtures, conexões e validações de forma concisa.

### 6. Helper Compartilhado de Integração (`database.SetupTestDatabase`)
- Testes de integração de infraestrutura (`pool_integration_test.go`, repositórios SQL, etc.) reutilizam o helper centralizado:
  ```go
  ctx, pool := database.SetupTestDatabase(t)
  ```
- O helper:
  - Valida `testing.Short()` e faz skip se necessário.
  - Carrega variáveis de ambiente do `.env`.
  - Configura timeout com cancelamento em `t.Cleanup`.
  - Conecta ao pool e registra o fechamento gracioso via `t.Cleanup(pool.Close)`.
  - Ignora o teste graciosamente (`t.Skipf`) se a base de dados não estiver alcançável.

## Mockery Workflow

Before creating or modifying tests requiring mocks, run from `services/app-api`:

```bash
mockery
```

Reuse the generated mocks located in `internal/test/mocks/`. Do not edit generated Mockery files manually.

## Assertions and Determinism

- Use `require` (from `testify/require`) when a failure makes subsequent assertions meaningless (e.g. `require.NoError(t, err)`, `require.NotNil(t, result)`).
- Use `assert` (from `testify/assert`) for independent property checks where seeing all failure details is valuable.
- Keep tests 100% deterministic: no sleeps, no reliance on external internet access, no shared mutable global state.

## Required Validation

Para testes unitários regulares:
```bash
go test -v ./...
go vet ./...
```

Para a suíte de testes de integração com o PostgreSQL ativo:
```bash
go test -tags=integration -v ./...
```

Run `go fmt ./...` whenever Go source formatting changes. Do not weaken or delete a valid test to make the suite pass.
